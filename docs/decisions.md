### 19.1 Decisions

| Date | Decision | Why |

### 19.2 Open questions

- [ ] Client shell: Tauri, Humble UI, or per-platform native. Requirement fixed in section 15.6. Due end of sprint 0.
- [ ] Salience scorer: the first ranking over resolved references. Recency and task linkage are enough for kernel-zero; decide the model before the demo.
- [ ] Memory field governance: who may prune another principal's authored fields on a shared object, and under which grant.
- [ ] Field conflict policy: last-writer-wins by `at` is the default. Decide whether any class needs a merge.
- [ ] Index threshold: when the Datascript rebuild from the log exceeds startup budget, move to XTDB. Measure in sprint 4.
- [ ] Loops as clients: resolved, loops are resident. Section 9.8.
- [ ] Demo task: ship a feature is the recommendation. Confirm or replace.
- [ ] Name: knowledge environment is the working term. The product needs one.
- [ ] Schema evolution: how an old event folds under a new apply function. Proposal: apply functions are versioned by event kind, and a migration is an Evaluation that appends, never rewrites.
- [x] Simplify, candidate 1: fold Workspace into Principal. A Workspace is an appliance with a runtime Field, byte-stream Fields, and a shell Model. One class fewer, and section 10 already treats it that way.
- [x] Simplify, candidate 2: a View is a Serialization whose Model is a listener. One renderer model, as section 8.5 claims. Removes a class and makes a person's view and an agent's context the same Object.
- [ ] Simplify, candidate 3: Adapter is a Model of kind adapter. The binding semantics of 5.10 become Fields on a Model. One class fewer.
- [ ] Simplify, candidate 4: Serialization as an arrangement, leaving four kernel classes. It is an Object with Fields; only the serializer is kernel code.
